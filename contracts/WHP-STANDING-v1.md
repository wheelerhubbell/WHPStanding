# WHP Standing v1 — first public cryptographic contract

Status: normative first-public-v1 contract. The earlier candidate is development provenance, not a released protocol version. This document and the closed schemas define one contract. TEST verification does not supply production authority, a sale, deployment, or LIVE issuance.

## Completed object and boundaries

One owner-authorized purchase produces one durable signed historical result after exact finalized settlement. A favorable result is a WHP Standing Mark v1. A negative result is an assessment record, never a Mark. Authentication and structural admission precede storage and payment work. Recovery reuses the original authorization; retrieval returns identical original bytes without another charge.

There are three separate objects. The Mark contains the issuance-time assessment. A registry snapshot reports current standing. A discovery resolution reports the current provider/service. Neither a registry change nor a service move changes the historical Mark. No signature alone establishes current standing. No discovery advertisement establishes epistemic need or institutional trust.

## Envelope and canonicalization

The envelope has exactly `protected`, `payload`, `signature`. `protected` has exactly `type`, `algorithm`, `canonicalization`, `key_id`. Type is `WHP-STANDING-MARK-v1` or `WHP-STANDING-ASSESSMENT-v1`; algorithm is `Ed25519`; canonicalization is `WHP-JCS-I1`. The key ID is lower-case SHA-256 of canonical Ed25519 DER SPKI bytes. Public keys and signatures use canonical padded base64. The signature input is UTF-8 canonical JSON of exactly `{protected,payload}`. The protected type supplies domain separation. Hash commitments use lower-case SHA-256; JSON hashes are over canonical UTF-8 bytes, file hashes over exact bytes.

Objects sort keys by UTF-16 code units. Arrays preserve order. Strings use JSON escaping, preserve Unicode without normalization, and reject lone surrogates. Only lexical JSON integers in [-9007199254740991,9007199254740991] are admitted. Negative zero, decimal or exponent number lexemes (including 1.0 and 1e0), duplicate keys, nonfinite values, malformed UTF-8, trailing content, and excessive nesting fail closed. Decimal token amounts remain uint256 decimal strings. General depth is 64; submissions reserve 16 envelope levels. Submission bytes are limited to 262144; authority bundles to 65536. Exact persisted Mark bytes include one final LF. Noncanonical input whitespace/key ordering may be parsed, but signatures always use canonical bytes; a registry file hash is never computed over a reserialization.

All semantic envelopes are CLOSED, including every nested discovery/meaning/verification object. Unknown or missing semantic fields, wrong types or versions, failed commitments, invalid authority, replay discrepancies, and unavailable/stale mandatory current evidence are failures, not warnings. A new semantic capability requires a new explicitly versioned contract. No generic extensions bag or candidate fallback exists. Arbitrary submitted `content` and preserved raw blockchain log evidence are opaque committed evidence, not protocol extension points. Their arbitrary keys cannot alter verification rules.

## Historical signed body

The exact payload fields are `version`, `environment`, `issuer`, `issuer_key_id`, `purchase_id`, `mark_id`, `issued_at`, `effective_at`, `expires_at`, `object`, `profile`, `profile_authorization`, `authority`, `submission`, `submission_hash`, `decision_record`, `decision_record_ref`, `standing`, `commerce`, `retrieval`, `limitations`, `discovery`, `current_status_rule`. `version` is `WHP-STANDING-RESULT-v1`; the protected type distinguishes Mark from negative assessment.

The full submitted signed graph is embedded. Its exact digest binds the request, quote and deterministic decision. The object ID/version/root identifies the same node in each location. Nodes retain locator, status, prior-version reference, content, epistemic status, permissions, qualifications, unknowns and blocked operations. COPY and identity-preserving COMPOSE, separately warranted transformations, graph closure/cycle rejection, authority, scope, jurisdiction and temporal intersections are independently replayed. No source-status or epistemic-force promotion is permitted. Diagnostic rule details are fixed text, not an additional claim.

The complete issuance-time profile is embedded and hash-bound by the submitted profile reference, root authorization, every authority certificate and quote. The profile ID/version/hash are exact, not a link to the latest profile. The verification material is also content-addressed and retained. A later current profile cannot retroactively change the embedded profile or old replay semantics. Institutional ratification is a separate root-signed, environment-specific act.

`decision_record` fixes the operation, bounds, outcome, permitted operations, component determinations, complete check trace, source-indexed unknowns, effective time, expiry, assessed boundary, exclusions and review triggers. `standing` exists only on an established result and equals exactly the decision's operation/components/bounds; otherwise it is null and `mark_id` is null. `limitations` equals the profile exclusions. `effective_at` equals the actual assessment time. Mark expiry is the minimum of the independently replayed expiry and issuer certificate expiry. Time intervals are half-open.

`authority` is the complete root-key/profile-authorization/certificate/revocation/status bundle admitted at issuance. Root-signed manifests bind the exact arrays, preventing selective omission. Issuer, source, transition, registry and discovery roles remain distinct. The payment recipient is never an issuer or root identity. A verifier's externally supplied root pin remains mandatory for policy-based trust. A mark-only reader can verify the self-certifying key identity and internal chain, but MUST report institutional/root-policy admission as NOT_ESTABLISHED rather than manufacture external trust from embedded material.

`commerce` embeds the original signed quote, exact x402 authorization, transaction identity and settlement proof. It binds buyer, request, recipient, amount, network, asset, resource, nonce and final transaction. The purchase identity is SHA256 of canonical `{domain:'WHP-STANDING-PURCHASE-v1',root_pin,buyer_key,client_reference}`. The payment nonce is SHA256 of canonical `{domain:'WHP-STANDING-PURCHASE-BINDING-v1',quote:<complete signed quote payload>}` with `0x` prefix. The payment identity separately binds network, asset, authorizer and nonce. TEST transfers are explicitly simulated. LIVE recipient is 0x1050eddd8282623b0c263ed6bdbd42370bbc28d3, network eip155:8453, native USDC. LIVE consensus/finality is independently rechecked against a verifier-admitted RPC; the embedded observation is not a consensus inclusion proof.

## Immutable discovery binding

`discovery` has exactly `format`, `artifact`, `issuer`, `capability`, `meaning`, `profile`, `resolution`, `verification`, `status`. Its format is `signed-artifact-discovery-v1`. It contains no current commercial endpoint or service origin.

`artifact` has `name`, `contract`, `historical`. `issuer` has `id`, `name`, `root_pin`, `institutional_attribution`. Issuer ID is `urn:sha256:<root-pin>`; its human-readable name remains an authorized label, not independent proof of legal institutional appointment. `capability` has `id`, `requirement_id`; the canonical root-qualified provider capability is `urn:whp:standing:v1:<root-pin>`, while the distinct vendor-neutral requirement is `urn:capability:machine-verifiable-standing:1`.

`meaning` has `determination`, `establishes`, `does_not_establish`, `claim_pointer`, `bounds_pointer`, `authority_pointer`, `provenance_pointer`, `qualifications_pointer`, `unknowns_pointer`, `limitations_pointer`. These are exact derived descriptions/pointers into the signed historical body; they cannot enlarge its claim. Negative assessments say that no standing was established. `profile` has `id`, `version`, `sha256`, `embedded_pointer`.

`resolution` has `id`, `format`, `authority_role`, `max_age_seconds`. Its ID is an immutable canonical ASCII HTTPS resolution URL with path `/.well-known/standing-resolution.json`, lowercase authority and no explicit default or zero-padded port (TEST may use explicit loopback HTTP), its format is `WHP-STANDING-RESOLUTION-v1`, and its delegated authority role is `DISCOVERY`. Resolution availability must be maintained when commercial hosting moves. Unreachability is an unresolved current route, never permission to guess a service. LIVE runtime requires an explicitly configured canonical discovery origin; it may differ from the current service origin.

`verification` has `algorithm`, `canonicalization`, `signed_fields`, `key_encoding`, `embedded_root_pointer`, `certificates_pointer`, `certificate_key_pointer`, `source_sha256`, `source_id`, `invocation`. The source ID is `urn:sha256:<source_sha256>` and identifies the exact separately implemented Python verifier bytes. Invocation contains exactly `arguments` and `test_arguments`, with public input placeholders for original Mark bytes, root pin and fresh registry bytes. Downloaded verifier code runs without network, secrets, writable host mounts or producer source. Integrity of downloaded code does not establish institutional trust or endorse arbitrary code.

`status` has `type`, `requires_fresh`, `max_age_seconds`; it requires a separately signed `WHP-REGISTRY-SNAPSHOT-v1` no more than 300 seconds old. A current-status failure does not erase historically valid issuance.

## Current resolution and service contract

The current resolution is a separate Ed25519 envelope, type `WHP-STANDING-RESOLUTION-v1`. Its payload has exactly `version`, `resolution_id`, `capability_id`, `environment`, `issuer_key_id`, `sequence`, `previous_hash`, `observed_at`, `valid_until`, `authority`, `provider`. It must match the Mark's immutable resolution/capability/environment/root bindings; validate the fresh root-signed trust manifest; and carry a currently valid, nonrevoked DISCOVERY delegation. Its validity is at most 300 seconds and cannot outlive the signed trust, profile authorization or delegation. `sequence` is the mapping publication revision; heartbeat observation-time renewal does not create a new revision. Revision zero has null `previous_hash`; later revisions commit the SHA256 of the preceding canonical `provider` object. A reader that observes consecutive revisions checks that link. A stateful reader rejects sequence rollback/equivocation; a first-contact reader cannot claim knowledge of unseen history.

`provider` has exactly `id`, `name`, `publisher`, `service_origin`, `compatible_requirements`, `contract`, `openapi`, `profile`, `material_url_template`, `registry_url_template`, `discovery_url`. `contract` and `openapi` each have `url`, `sha256`, binding their current canonical JSON. `profile` has `id`, `version`, `sha256`, `url`; this is the CURRENT offer's profile, not a replacement for the Mark's embedded profile. The material template substitutes a lowercase SHA256, the registry template substitutes the purchase ID. These are current resolution instructions, never historical standing claims. Only a verified resolution may authorize a cross-origin service move. Redirects and unrelated origins are rejected.

The current purchase contract hash-binds both published JSON Schemas and describes the schema, authentication recipe, profile, supported assessment bounds, provider requirement compatibility, exact quote/nonce relation and payment terms. It includes a boundary-only construction recipe for an external JSON object. That recipe must preserve the external content and contemplated operation, explicitly keep unestablished source authority unknown, and never promise a favorable result. A cold consumer creates an Ed25519 HTTP authentication key, not a wallet; it obtains HTTP 402 without a payment signature and never pays.

## Current registry and authority

A fresh registry snapshot binds the exact original result file hash, purchase and Mark IDs, signed append-only events, current authority bundle, observation time and validity. Root-authorized withdrawal/supersession is terminal. Expiry is calculated; post-issuance revocation can limit standing without rewriting historical bytes. Review receipts record appeals, never adjudication or a new Mark. Registry snapshots, events and commands are closed semantic objects and are independently validated. A valid historical signature is reported separately from ACTIVE, LIMITED, EXPIRED, WITHDRAWN and other current states.

## Vendor-neutral discovery and TEST proof boundary

STANDING-NEED-v1 describes missing evidence, provenance, transformation warrant, authority, preservation and blocking unknowns independently of provider. Recognition never tests for a missing WHP brand. A generic directory interface returns multiple provider candidates; compatibility is selected by the requirement ID and explicit capabilities, not provider name, order or a WHP URL. Directory membership is discovery, not institutional authority.

Cold A starts with one Mark file, no injected product URLs, paths, pins or descriptions. Cold B starts with an external object, contemplated action and the vendor-neutral interface; only the generic directory endpoint is bootstrap configuration. Cold C joins A's independent reading to a later unsupported object/action, neutral need, provider discovery and the next actual 402 boundary. Isolated processes receive only their declared files. Their source has no WHP-specific vocabulary, URLs, repository imports or fixture access. Adversarial mutation, missing evidence, stale/revoked status, incompatible directories and hard-coded-provider traps fail closed.

These executions establish PROPAGATION-PROVEN at TEST level only. They do not claim public search indexing, LIVE issuer admission, outside buyer funds, deployment, a sale or LIVE issuance. Those require separate evidence.

String length limits count Unicode scalar values. The complete machine grammar is in `schemas/`; the standalone Python verifier embeds that exact grammar. The constructor validates it before returning signed bytes. Unknown grammar keywords fail closed. Arbitrary submitted `content` and raw chain logs are evidence values, not semantic extension fields.

The production operator must retain the discovery publication revision and predecessor hash across restarts and changes of hosting. A memory-only process history cannot prove unseen history. TEST fixtures exercise observable revision progression, rollback rejection and service relocation; they are not a production deployment.

The distributed reference verifier checks its advertised source commitment against its own exact source bytes. Equivalent independently written verifiers may instead check the committed reference material separately; the source commitment is not a license to replace the frozen semantics. Later corrections must preserve retrievability of already-committed reference material. The candidate never became such a public compatibility commitment.
